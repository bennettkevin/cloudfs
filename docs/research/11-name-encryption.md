# Spike 11: Encrypted file names and blind index

- **Issue:** #14
- **Status:** Decided. See [ADR-0017](../adr/0017-encrypted-names-and-blind-index.md): all six recommendations accepted on 2026-11-24. Re-check golang/go#46101 when upgrading `golang.org/x/text`.
- **Question:** With end-to-end encryption ([ADR-0007](../adr/0007-end-to-end-encryption.md)), should file and folder names be encrypted, and if so, how does the server still enforce case-insensitive unique names per folder ([ADR-0005](../adr/0005-conflict-resolution.md))? What does it cost?

Everything marked **measured** was run on 2026-11-24 on an Apple M5 MacBook (macOS 26 / Darwin 25.6, APFS, Go 1.27.4, `golang.org/x/text` v0.44.0 = Unicode 17.0.0, `golang.org/x/crypto` v0.59.0) using [`spikes/11-name-encryption/`](../../spikes/11-name-encryption/). Anything else is from a cited source or marked *unverified*.

---

## 0. Decisions this builds on

- Nodes have stable server-assigned IDs; path = `parent_id` + `name` ([ADR-0004](../adr/0004-stable-file-ids.md)).
- The server enforces **case-insensitive unique live names per folder**, no cycles, live parent ([ADR-0005](../adr/0005-conflict-resolution.md)). Conflicted-copy names are generated by the client.
- Names go to the server in Unicode NFC; each device keeps its own spelling on disk ([ADR-0014](../adr/0014-local-change-detection.md)).
- Tombstones keep the name during the 30-day trash; purge drops it ([ADR-0012](../adr/0012-deletes-tombstones-and-trash.md)).
- Key hierarchy (master key → HKDF sub-keys, XChaCha20-Poly1305) is sketched in [research 03](03-encryption.md) §3 and designed in phase 1.

---

## 1. What the server actually needs names for

| Server job | Needs the plaintext name? |
|---|---|
| Unique live name per folder, case-insensitive | **No.** Equality is enough → blind index (section 2) |
| No cycles, live parent | No. Uses IDs only |
| Conflicted-copy names | No. The client builds them ([ADR-0005](../adr/0005-conflict-resolution.md)) |
| Trash listing, restore | No. The client decrypts names for display (`cloudfs trash`) |
| Purge to a stub | No. It deletes the name columns |
| Sorting, search, admin/debug display | Would be nice. Lost with encryption (section 6) |

**Takeaway:** the server needs one thing from names: "do these two names in the same folder collide?". A keyed hash answers that without revealing the name.

## 2. Design under test: encrypted name + blind index

**Jargon:**
- **Blind index:** a keyed hash (HMAC) of a normalized value. The server can compare two indexes for equality, but without the key it can't compute one for a guessed name.
- **Associated data (AD):** extra bytes the AEAD authenticates but doesn't encrypt. Decryption fails if they don't match.

What the client sends with every create, rename or move:

| Field | Value | Server use |
|---|---|---|
| `name_ct` | `nonce(24) ‖ XChaCha20-Poly1305(name_key, pad32(len ‖ NFC(name)), AD = node_id ‖ parent_id)` | Stores it, returns it to clients |
| `name_index` | `HMAC-SHA256(index_key, parent_id ‖ IndexForm(name))` | Unique constraint on `(parent_id, name_index)` for live nodes |

- **Randomized encryption** (random nonce): the same name encrypts differently every time.
- **AD binds the name to its node and parent.** The server can't swap names between nodes or silently move a node to another folder: the client's decryption would fail (measured: `TestRoundTripAndBinding`).
- **`parent_id` inside the HMAC** means `README.md` in two different folders gives two unrelated indexes. The server only learns equality inside one folder, which is exactly what it needs to enforce.
- **Separate keys** `name_key` and `index_key`, both HKDF sub-keys of the master key (phase 1 key hierarchy).
- **Padding** to a multiple of 32 bytes hides the exact name length (section 7).
- **Folder rename:** only that folder's row changes. Children keep their ciphertext and index, because their `parent_id` (the folder's ID) doesn't change.
- **Move:** the client sends a new `name_ct` and `name_index` for the new parent. It already sends the name on every move, so this adds no round trip.

## 3. Randomized vs deterministic name encryption

**Jargon:** **AES-SIV** is a *deterministic* AEAD: the same name and key always give the same ciphertext. It's misuse-resistant (no nonce to get wrong).

| | Randomized (XChaCha20-Poly1305) | Deterministic (AES-SIV) |
|---|---|---|
| Same name, same node, twice (e.g. rename away and back) | Different ciphertext | Same ciphertext: leaks "renamed back" |
| Needs a blind index for uniqueness? | Yes | Could compare ciphertexts directly, but only case-*sensitively* (it encrypts the exact name). Case-insensitive uniqueness still needs a separate index |
| Go library | `golang.org/x/crypto` (already used for chunks) | Not in x/crypto. Syncthing uses `miscreant.go` (archived since 2020; checked 2026-11-24 via GitHub API). Alternatives are small and young (`secure-io/siv-go`: last push 2018; `jedisct1/go-aes-siv`: created 2026-01) |
| Speed per name (measured) | 550 ns (incl. padding and random nonce) | 266 ns (`miscreant`) |

**Why do Syncthing and Cryptomator use AES-SIV, then?** Their encrypted name *is* the file path on untrusted storage, so a client must be able to compute "the ciphertext for `notes.md`" to look it up ([Cryptomator docs](https://docs.cryptomator.org/security/vault/), [Syncthing untrusted devices](https://docs.syncthing.net/users/untrusted.html), both cited in [research 03](03-encryption.md)). CloudFS addresses nodes by ID and never looks a node up by name on the server, so it doesn't need determinism. Cryptomator also needs name shortening for long ciphertexts on real filesystems; CloudFS stores ciphertexts in Postgres, so it doesn't.

**Takeaway:** randomized encryption leaks less, reuses the primitive and library already chosen for chunks, and the speed difference is irrelevant (section 5).

## 4. What exactly gets hashed: normalization and case folding

Plain `strings.ToLower` is not enough. It misses `ß` vs `SS`, Greek final sigma, ligatures, and NFC vs NFD forms of accented letters.

### What APFS considers "the same name" (measured)

The test created the first name on this Mac's APFS volume (case-insensitive, the macOS default) and checked whether the second name then existed. `TestAPFSLive` repeats this on any case-insensitive volume.

| Pair | APFS same? | Full case fold + canonical (NFD) | NFKC + case fold |
|---|---|---|---|
| `notes.md` / `NOTES.md` | yes | yes | yes |
| `Straße` / `STRASSE` | **yes** | yes | yes |
| `ß` / `ẞ` | yes | yes | yes |
| `café` (NFC) / `café` (NFD) | yes | yes | yes |
| `ﬁle` (ligature) / `file` | **yes** | yes | yes |
| `ς` / `σ` / `Σ` (Greek sigmas) | yes | yes | yes |
| `Ꭰ` / `ꭰ` (Cherokee) | yes | yes (*after the fix below*) | yes |
| `İ` / `i`, `ı` / `I`, `ı` / `i` (Turkish) | no | no | no |
| `①` / `1`, `Ａ` / `A`, `ｶ` / `カ`, `x²` / `x2`, `ǆ` / `dž` | **no** | no | **yes** |

**Finding:** APFS's rule matches **Unicode canonical caseless matching**: NFD, then full default case folding, then normalize again (Unicode §3.13, definition D145; *from prior knowledge, not re-fetched*). It does *not* apply compatibility normalization (NFKC). Every pair matched (`TestIndexFormMatchesAPFS`).

So the client computes:

```
IndexForm(name) = NFC( fold( NFD(name) ) )
```

where `fold` is full default case folding (`CaseFolding.txt` statuses C + F). Ending in NFC instead of NFD gives the same equalities in a shorter string.

### A bug in Go's case folding (measured, known upstream)

`golang.org/x/text/cases.Fold()` disagreed with Unicode on exactly **86 code points**: the Cherokee capitals U+13A0–U+13F5. An exhaustive check compared every code point against Unicode 17.0.0's `CaseFolding.txt`.
- Unicode folds Cherokee *to the capitals*: since Unicode 8.0, new lowercase Cherokee letters were added that fold to the existing uppercase ones, to keep folding stable.
- x/text folds the capitals to the small letters, so `Ꭰ` and `ꭰ` get different indexes.
- This is an open Go issue since 2021: [golang/go#46101](https://github.com/golang/go/issues/46101).
- **Fix in the spike:** after `cases.Fold`, map Cherokee small letters back to capitals. `TestFoldMatchesUnicode` now checks all 1.1 million code points against the pinned `CaseFolding.txt` with **0 mismatches**.

### Stability across Unicode versions

- The Unicode **Case Folding Stability** policy guarantees that `toCasefold(toNFKC(S))` gives the same result in every later version, for assigned characters. Formally it covers NFKC-normalized strings ([stability policy](https://www.unicode.org/policies/stability_policy.html), fetched 2026-11-24).
- **Case Pair Stability:** characters that form a case pair stay a pair, and characters that don't never become one.
- CloudFS uses canonical (NFD) folding to match APFS, so it falls slightly outside the *formal* guarantee. In practice, fold mappings of already-assigned characters don't change; the Cherokee change happened through *new* characters precisely to keep this true.
- **Mitigations:**
  - pin `x/text`, and keep the exhaustive test against a checked-in `CaseFolding.txt` of the same Unicode version
  - store a `name_scheme` number with every name, so a future rule change can be migrated: clients recompute indexes and re-commit

### Other filesystems

- **Linux ext4/XFS/Btrfs** are case-sensitive by default (*prior knowledge, not re-checked*). `notes.md` and `NOTES.md` can coexist locally; the server rejects the second one, and it becomes a conflicted copy (ADR-0005, already decided).
- **Windows NTFS** (later): uses its own uppercase table, not Unicode case folding. Turkish dotless `ı` may collide with `i` there (*unverified*). This belongs to the Windows work behind the watcher interface (ADR-0014).

## 5. Compute cost (measured)

`go test -bench . -count 3`, one goroutine, Apple M5. The corpus is 10,000 synthetic names: mostly ASCII, some accented Latin, CJK, Hangul, Greek and emoji; average 21.7 bytes.

| Operation | Time per name | Notes |
|---|---|---|
| `IndexForm` (NFD → fold → NFC) | ~405 ns | |
| Blind index (IndexForm + HMAC-SHA256) | ~705 ns | |
| Encrypt name (NFC, pad, random nonce, XChaCha20-Poly1305) | ~550 ns | |
| Decrypt name | ~320 ns | |
| **Encrypt + index (per create/rename/move)** | **~1.27 µs** | |
| AES-SIV encrypt (comparison) | ~266 ns | `miscreant` |

| At scale | Time |
|---|---|
| 10,000 names, encrypt + index | 16–24 ms |
| 100,000 names, encrypt + index | 126–149 ms |
| 100,000 names, decrypt (full listing on reconcile) | ~32 ms (320 ns × 100k) |

**Compared with work the client already does per chunk:**

| Baseline (measured) | Time | Name operations in the same time |
|---|---|---|
| Encrypt one 1 MiB chunk, XChaCha20-Poly1305 (~1.3 GB/s) | ~0.79 ms | ~620 |
| Keyed chunk ID of 1 MiB, HMAC-SHA256 (~3 GB/s) | ~0.35 ms | ~275 |
| One HTTPS round trip to the API (*not measured; typically ≥ 1 ms on LAN, tens of ms over the internet*) | | ≥ 800 |

**Takeaway:** name encryption plus the blind index for 100,000 files costs about as much CPU as encrypting 160 MB of file content, which is a fraction of a percent of an initial sync. **Compute cost is not a reason to skip name encryption.**

## 6. Non-CPU costs

- **Storage (measured):** average name 21.7 bytes plaintext → 78.2 bytes ciphertext, plus a 32-byte index. About 110 bytes per node instead of 22: ~11 MB instead of ~2 MB for 100,000 nodes. Negligible.
- **No server-side sorting or search by name.** Listings come back in ID order; the client sorts after decrypting. Search is client-side over its local baseline, which already has plaintext names.
- **Debugging:** database rows and server logs show ciphertext. Debugging needs a client command that decrypts (`cloudfs ls --ids`, `cloudfs debug node <id>`). The server logs node IDs, never names, which is also better for privacy.
- **Protocol:** one extra field (`name_index`) on create, rename, move and restore. Restore re-checks the index against live siblings, and a collision follows ADR-0005's name-collision rule.
- **Key rotation (phase 1):** rotating `name_key` or `index_key` means every client re-encrypts and re-indexes all names. At ~1.3 µs each, that's CPU-cheap, but it is a full re-commit of every node.
- **Recovery:** losing the key loses the names as well as the content. That's no change from ADR-0007.

## 7. What still leaks

| Leak | Detail | Mitigation |
|---|---|---|
| Name equality within one folder | Inherent: that's what uniqueness needs. Includes "a deleted name was reused in the same folder" while the tombstone keeps its index | Drop `name_index` at purge (30 days) |
| Approximate name length | Padded to 32-byte blocks: names ≤ 31 bytes look identical; longer ones reveal their 32-byte bucket | Larger blocks (e.g. 64) cost more storage for little gain; ≤ 31 bytes covers most names (corpus average 21.7) |
| Tree shape, kinds, sizes, times | Unchanged by this spike: `parent_id`, file/folder, chunk counts and padded sizes, timestamps | Accepted in ADR-0007/ADR-0010 |
| Guessing a name from its index | Not possible without `index_key` (keyed HMAC) | Keep `index_key` separate from `name_key` |

## 8. Data model and protocol changes (if accepted)

- `nodes.name` (plaintext) is replaced by:
  - `name_ct` (bytea)
  - `name_index` (bytea, 32 bytes)
  - `name_scheme` (smallint)
- Unique constraint `(parent_id, name_index)` where the node is live. Tombstones keep `name_ct` and `name_index` during the trash period; purge sets both to NULL.
- Create, rename, move and restore carry `name_ct` + `name_index`; the server returns `name_ct` in listings and changes.
- Client baseline keeps the plaintext name (it already does, [design §9](../design.md)).

### New user data stored or transmitted

| Data | Where | Notes |
|---|---|---|
| `name_ct` | Postgres | Replaces the plaintext name. **Less** exposed than today's design |
| `name_index` | Postgres | Keyed hash; reveals equality within a folder only |

Net effect: less user data readable by the server. The privacy policy question is unchanged (none yet; self-hosters provide their own).

## Recommendation (accepted 2026-11-24)

1. **Encrypt names in v1** with randomized XChaCha20-Poly1305: AD = `node_id ‖ parent_id`, padded to 32-byte blocks, separate HKDF sub-key.
2. **Blind index** `HMAC-SHA256(index_key, parent_id ‖ IndexForm(name))`, unique per folder for live nodes, dropped at purge.
3. **Equality rule = canonical caseless matching** (NFD → full case fold → NFC), which matches APFS exactly. Not NFKC, which would make `①.txt` and `1.txt` collide, and not plain lowercasing.
4. **Own the fold function**: `x/text` plus the Cherokee fix, pinned `x/text`, exhaustive test against a checked-in `CaseFolding.txt`, and a `name_scheme` field for future migrations.
5. **No AES-SIV.** It's not needed when nodes are addressed by ID, leaks more, and has no healthy Go library.

## Decisions for the user

1. **Encrypt names?**
   - Options: (a) yes, randomized; (b) yes, deterministic (AES-SIV); (c) no, plaintext names.
   - **Recommended: (a).** Costs ~1.3 µs per name. Hides names from the server and the cloud provider, which is the point of ADR-0007. (c) leaves the most sensitive metadata (file names often say what's inside) readable.
2. **What counts as the "same name"?**
   - Options: (a) canonical caseless matching (matches APFS); (b) NFKC + case fold (formally stable, broader); (c) lowercase only.
   - **Recommended: (a).** Same behaviour as the Mac filesystem, measured. (b) would turn `①.txt` vs `1.txt` into conflicted copies even though no filesystem we target confuses them. (c) misses `ß`/`SS`, NFD, ligatures and Greek sigma.
3. **Index scope.**
   - Options: (a) per folder (`parent_id` in the HMAC); (b) global.
   - **Recommended: (a).** Uniqueness is per folder anyway, and (b) would reveal the same name across folders.
4. **Bind names to node and parent (AD)?**
   - Options: (a) `node_id ‖ parent_id`; (b) `node_id` only; (c) none.
   - **Recommended: (a).** The server can't silently move files or swap names; the client sends a new ciphertext on every move anyway.
5. **Name padding.**
   - Options: none; 32-byte blocks; 64-byte blocks; pad everything to 255.
   - **Recommended: 32-byte blocks.** Most names fall in the first bucket; storage stays tiny.
6. **Unicode bug handling.**
   - **Recommended:** keep the Cherokee fix plus the exhaustive test, pin `x/text`, and store `name_scheme`. Re-check golang/go#46101 when upgrading `x/text`.
